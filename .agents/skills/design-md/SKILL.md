# DESIGN.md

`DESIGN.md` at the repo root is the single source of truth for the site's visual
identity. Tokens in YAML are normative; the Markdown prose explains why they
exist and how to apply them. Read it before touching styles; update it when the
design system changes.

Full spec from the CLI at any time:

```bash
npx -y -p "@google/design.md" designmd spec
npx -y -p "@google/design.md" designmd spec --rules
```

> Windows/PowerShell: use the `designmd` alias exactly as shown. The bare
> `design.md` bin name collides with the `.md` file association and can produce
> no output.

## File shape

```md
---
version: alpha
name: <system name>
description: <one line>
colors:
  primary: "#1A1C1E"
  secondary: "#6C7278"
  tertiary: "#B8422E"
  neutral: "#F7F5F2"
typography:
  h1:
    fontFamily: Public Sans
    fontSize: 3rem
    fontWeight: 600
    lineHeight: 1.1
  body-md:
    fontFamily: Public Sans
    fontSize: 1rem
rounded:
  sm: 4px
  md: 8px
spacing:
  sm: 8px
  md: 16px
components:
  button-primary:
    backgroundColor: "{colors.tertiary}"
    textColor: "{colors.neutral}"
    rounded: "{rounded.sm}"
    padding: 12px
---

## Overview
...

## Colors
...

## Typography
...
```

- Sections use `##` and must appear in this order when present: Overview,
  Colors, Typography, Layout, Elevation & Depth, Shapes, Components,
  Do's and Don'ts.
- Token references use `{colors.primary}` style paths and must resolve.
- Every color/typography/spacing/rounded value used in code should exist as a
  token; components should reference tokens, not raw values.
- Do not invent palettes or typefaces when one is already documented. If a
  needed token is missing, add it to DESIGN.md first, then use it.

## Commands

```bash
# validate (exit 1 on errors)
npx -y -p "@google/design.md" designmd lint DESIGN.md

# compare before/after (exit 1 on regressions)
npx -y -p "@google/design.md" designmd diff DESIGN.md DESIGN-old.md

# export for the stack in use
npx -y -p "@google/design.md" designmd export --format css-vars DESIGN.md
npx -y -p "@google/design.md" designmd export --format css-tailwind DESIGN.md
npx -y -p "@google/design.md" designmd export --format json-tailwind DESIGN.md
npx -y -p "@google/design.md" designmd export --format dtcg DESIGN.md
```

All commands print JSON by default. Read the `findings` and `summary` fields
rather than re-parsing the file by eye.

## Workflow

1. Before a visual build or redesign, read `DESIGN.md` (create it if absent,
   using the spec above).
2. Implement UI from tokens (CSS custom properties or the framework theme
   generated by `export`).
3. Run `lint` and fix errors; treat `contrast-ratio`, `missing-primary`,
   `missing-typography`, `orphaned-tokens` and `broken-ref` warnings as real.
4. If the system changed on purpose, update `DESIGN.md` in the same change and
   verify with `diff`.

## Boundaries

- DESIGN.md describes identity, not page structure or content.
- Do not commit generated export files unless the app imports them; prefer
  generating at build time or pasting tokens into the stack's theme layer.
- Hallmark (`.agents/skills/hallmark`) owns page design and slop checks; this
  skill owns the token document. Use them together: Hallmark picks the
  material, DESIGN.md records it.
